## 1. 项目背景与目标

### 1.1 项目起源

简历优化助手 v3.0 已实现单次 LLM 调用的简历优化功能（粘贴文本 → 输出四栏结果）。但存在两个核心局限：

1. **无自审机制**：LLM 一次生成即输出，没有自我检查和改进环节
2. **无文件支持**：用户只能粘贴纯文本，无法直接上传 PDF/DOCX 简历

本项目的目标是将 v3.0 的"工具"升级为"Agent"——具备自我审查和迭代改进能力的智能体。

### 1.2 什么是 Agent，为什么重要

**Agent ≠ 单次 LLM 调用。** Agent 的核心特征是：

```
单次调用：输入 → LLM → 输出（质量取决于 prompt 好坏，无自我修正）
Agent：   输入 → 规划 → 执行 → 自审 → 改进 → 输出（多轮迭代，质量内建）
```

对用户而言，Agent 意味着：
- 输出质量更高（自审过了至少一轮）
- 过程可解释（能看到 Agent 发现了什么问题、怎么改的）
- 体验更智能（像一个助手在干活，不像一个转换器）

### 1.3 产品定位

> **一句话**：上传简历/粘贴经历 → Agent 自动优化 + 自我审查 + 改进 → 下载 DOCX，一键完成。

- **目标用户**：求职者（校招/社招），需要快速产出高质量简历文案
- **使用场景**：投简历前发现经历描述太弱，需要 AI 润色优化
- **与 v3.0 的关系**：v3.0 保留为学习见证；Agent 项目是独立升级作品

## 2. 用户场景

### 2.1 核心场景

| 场景 | 用户 | 动作 | 结果 |
|------|------|------|------|
| 上传简历优化 | 有 PDF/DOCX 简历的用户 | 拖拽文件 → 点按钮 → 等 30 秒 → 看结果 → 下载 DOCX | 拿到优化后的简历文件 |
| 粘贴经历优化 | 想快速试试的用户 | 粘贴文本 → 点按钮 → 等 30 秒 → 看结果 → 下载 DOCX | 同上 |
| 追加修改 | 对结果某段不满意的用户 | 在追问框输入"第三段偏产品方向" → Agent 针对性改版 | 拿到调整后的版本 |

```

    │
    ├─ 点击「🚀 开始优化」
    │
    ├─ 等待，看到分步进度：
    │   "📄 正在解析简历…"
    │   "✍️ 正在优化…"
    │   "🔍 Agent 正在自审…"
    │   "🔧 正在改进…"
    │   "📥 正在生成 DOCX…"
    │
    ├─ 看到结果：
    │   ├─ 四栏对比（原句/问题/优化/理由）
    │   ├─ Agent 自审改进痕迹
    │   ├─ Agent 自评总结
    │   └─ 📥 下载 DOCX 按钮
    │
    └─ [可选] 追问框输入修改意见 → Agent 改一版
```

## 3. 功能需求

### 3.1 功能清单

| 优先级 | 功能 | 说明 |
|--------|------|------|
| **P0** | 简历内容解析 | 支持 PDF/DOCX 文件上传（≤10MB）+ 文本粘贴 |
| **P0** | Agent 优化 + 自审 | 两轮优化：首轮生成 → 自审挑毛病 → 二轮改进 |
| **P0** | 结果展示 | 四栏对比 + Agent 自审痕迹 + 自评总结 |
| **P0** | DOCX 下载 | 生成格式化 Word 文档 |
| **P0** | 分步进度展示 | 等待期间逐步更新状态，降低焦虑 |
| **P0** | 分步错误处理 | 每步独立兜底，告知用户"哪里出错 + 怎么办" |
| **P1** | 目标岗位/公司输入 | 主页面可选填，填入后优化更定向 |
| **P1** | 一轮追问 | 结果后支持一次追加修改指令 |
| **P2** | RAG 知识增强 | Agent 自主决定是否检索知识库（工具化） |
| **P2** | 逐步确认模式 | 高级用户可选每步手动确认 |

### 3.2 核心功能详述

#### 3.2.1 简历内容解析

- **文件上传**：支持 PDF、DOCX，大小上限 10MB，拖拽上传
- **文本粘贴**：保留文本框输入，与上传互斥（二选一）
- **解析策略**：
  - PDF：提取文本内容，含基本段落结构保留
  - DOCX：提取文本 + 段落样式
  - 粘贴文本：直接使用
- **解析失败**：提示用户"文件可能是图片扫描件，建议粘贴文本"

#### 3.2.2 Agent 优化流程（核心）

Agent 执行固定的两轮优化流程：

```
┌─────────────────────────────────────────┐
│ 第 1 轮：初始优化                         │
│ 输入：简历原文 + 目标岗位/公司（可选）      │
│ 输出：四栏结果（原句/问题/优化/理由）       │
└─────────────────────────────────────────┘
                    ↓
┌─────────────────────────────────────────┐
│ Agent 自审                               │
│ 输入：第 1 轮优化结果                     │
│ 动作：逐条检查，挑出具体缺陷               │
│ 检查维度：                                │
│   - 量化数据是否充分？[建议核实] 是否合理？ │
│   - 动词是否有冲击力？                     │
│   - STAR 结构是否完整？                    │
│   - 是否突出了个人贡献？                   │
│   - 技术关键词是否准确？                   │
│ 输出：缺陷清单 + 改进方向                  │
└─────────────────────────────────────────┘
                    ↓
┌─────────────────────────────────────────┐
│ 第 2 轮：针对性改进                       │
│ 输入：第 1 轮结果 + 自审缺陷清单           │
│ 动作：只修改被标记为缺陷的部分             │
│ 输出：改进后的四栏结果                     │
└─────────────────────────────────────────┘
```

**关键设计决策：固定 2 轮**
- 2 轮足够展示 Agent 自我改进价值
- 3 轮边际收益递减
- 动态轮数有死循环风险，且用户无法预期等待时间

#### 3.2.3 结果展示

屏幕展示分为四个区域：

1. **四栏对比**：最终版的原句/问题分析/优化版本/优化理由
2. **Agent 自审痕迹**：展示"第 1 轮 → 自审发现了什么问题 → 第 2 轮改了什么"
3. **Agent 自评总结**：Agent 用一段话说明本次优化的重点和效果（定性描述，非定量打分）
4. **操作区**：下载 DOCX 按钮 + 追问输入框

**设计理由**：
- 四栏格式经过 v3.0 验证，用户已熟悉
- 自审痕迹是 Agent 区别于普通 LLM 的核心证据
- 自评总结替代定量打分——LLM 自评分数无 Ground Truth，定性描述更诚实

#### 3.2.4 DOCX 生成

- 内容：优化后的简历全文 + 优化要点摘要
- 格式：正文宋体/小四，标题黑体加粗，页边距标准 A4
- 文件名：`简历优化_{时间戳}.docx`

#### 3.2.5 分步进度展示

等待期间（预计 20-40 秒）依次展示步骤状态：

| 步骤 | 状态文案 | 预计耗时 |
|------|---------|---------|
| 1 | 📄 正在解析简历… | 1-3 秒 |
| 2 | ✍️ 正在优化（第 1 轮）… | 5-10 秒 |
| 3 | 🔍 Agent 正在自审… | 5-10 秒 |
| 4 | 🔧 正在改进（第 2 轮）… | 5-10 秒 |
| 5 | 📥 正在生成 DOCX… | 1-2 秒 |

使用 Streamlit 的 `st.status` 组件实现，通过 `st.write()` 更新当前步骤文字。

#### 3.2.6 分步错误处理

每个步骤独立捕获错误，分类处理：

| 错误类型 | 类别 | 用户看到 | 用户能做什么 |
|---------|------|---------|------------|
| 文件解析失败（扫描件） | A（可修复） | "❌ 无法解析文件，可能是图片扫描件。请尝试粘贴文本。" | 切换到文本粘贴 |
| 文件过大 | A（可修复） | "❌ 文件超过 10MB，请压缩后重试。" | 压缩文件 |
| API Key 无效 | A（可修复） | "❌ API Key 无效，请检查设置。" | 更换 Key |
| 免费额度用完 | A（可修复） | "❌ 免费次数已用完，请填写自己的 API Key。" | 填 BYOK |
| LLM 调用超时 | B（不可修复） | "⚠️ 优化超时，请稍后重试。" | 重试 |
| LLM 返回格式异常 | B（不可修复） | "⚠️ 优化结果解析失败，请重试。" | 重试 |
| DOCX 生成失败 | B（不可修复） | "⚠️ 文档生成失败，但优化结果可在页面查看。" | 手动复制 |

#### 3.2.7 一轮追问

结果展示后，页面底部提供追问输入框：

- 占位文案："对结果不满意？告诉 Agent 怎么改（例如：第三段偏产品方向、整体太长了）"
- 触发：用户输入 + 点击"再次优化"
- 行为：Agent 基于当前结果 + 用户反馈，执行一轮针对性修改
- 限制：仅一轮。追问后如仍不满意，用户可重新上传/粘贴开始新流程

## 4. MVP 范围

### 4.1 包含

- ✅ 文件上传（PDF/DOCX，≤10MB，拖拽）+ 文本粘贴
- ✅ Agent 两轮优化（优化 → 自审 → 改进）
- ✅ 四栏结果展示 + 自审痕迹 + 自评总结
- ✅ DOCX 下载
- ✅ 分步进度展示
- ✅ 分步错误处理
- ✅ 目标岗位/公司输入（主页面可选填）
- ✅ 一轮追问

### 4.2 不包含（后续迭代）

- ⬜ RAG 知识库增强（Agent 工具化）
- ⬜ 逐步确认模式（高级选项）
- ⬜ 多轮对话（超过一轮追问）
- ⬜ 图片/扫描件 OCR 支持
- ⬜ 用户系统（注册/登录/历史记录永久存储）
- ⬜ 免费额度系统
- ⬜ 多模型切换（MVP 固定 DeepSeek）
- ⬜ PRD 生成 / 用户调研 / 数据看板（老项目功能，不迁移）

## 5. 非功能性需求

### 5.1 性能

| 指标 | 目标 | 说明 |
|------|------|------|
| 文件解析 | ≤3 秒 | PDF/DOCX 文本提取 |
| LLM 首轮优化 | ≤10 秒 | 依赖 DeepSeek API |
| Agent 自审 | ≤10 秒 | 同上 |
| LLM 二轮改进 | ≤10 秒 | 同上 |
| DOCX 生成 | ≤2 秒 | 本地文件写入 |
| **全流程** | **≤40 秒** | 用户可接受的等待上限 |

### 5.2 可用性

- 进度可见：等待期间至少更新 5 次步骤状态
- 错误可操作：每个错误提示必须包含用户下一步动作
- 文件拖拽：Streamlit 原生支持，无需额外实现

### 5.3 兼容性

- 浏览器：Chrome/Edge/Firefox 现代版本
- 部署：本地（`streamlit run`）/ Streamlit Cloud
- 格式：PDF 1.4+，DOCX（Office 2007+）

## 6. 技术方案概要

| 层级 | 选型 | 理由 |
|------|------|------|
| 前端框架 | Streamlit | 快速搭建，Python 全栈，已有经验 |
| LLM | DeepSeek（deepseek-chat） | 性价比高，中文理解好 |
| Agent 架构 | 手写 Agent Loop | MVP 阶段无需 LangChain 等重型框架；手写透明可控，面试时能清楚解释 |
| PDF 解析 | PyMuPDF（fitz） | 轻量快速，纯文本提取够用 |
| DOCX 解析 | python-docx | 读 DOCX 文本 + 写 DOCX 文件 |
| DOCX 生成 | python-docx | 格式化输出，支持中文字体 |
| 错误处理 | 每步 try/except + 分类提示 | 分步兜底，A 类引导修复 B 类降级提示 |

### Agent Loop 架构

```python
# Agent 核心流程（伪代码）
def agent_optimize(resume_text, target_role, target_company):
    # Step 1: 第一轮优化
    round1 = llm.generate(optimize_prompt(resume_text, target_role, target_company))
    
    # Step 2: Agent 自审
    review = llm.generate(review_prompt(round1))
    
    # Step 3: 第二轮改进
    round2 = llm.generate(improve_prompt(round1, review))
    
    # Step 4: Agent 自评总结
    summary = llm.generate(self_assessment_prompt(resume_text, round2, review))
    
    # Step 5: 生成 DOCX
    docx_path = generate_docx(round2, summary)
    
    return {
        "result": round2,
        "review_trace": review,    # 自审痕迹
        "self_assessment": summary, # 自评总结
        "docx_path": docx_path,
    }
```

**为什么手写不用框架**：
- 本项目 Agent 流程固定（2 轮优化），不需要框架的动态规划能力
- 手写代码 ~50 行，引入框架增加 500MB 依赖 + 黑盒风险
- 面试时能讲清楚每行代码的决策逻辑

## 7. 数据指标

| 指标 | 定义 | 目标 |

## 附录 A：产品决策依据

所有关键决策及理由见 [decisions.md](decisions.md)，核心原则：

1. **MVP 优先验证核心价值**：Agent 自审能力是本产品区别于 v3.0 的本质差异，其他功能（RAG、多轮对话、逐步模式）围绕它展开但不抢戏
2. **诚实优于美化**：砍掉无 Ground Truth 的定量评分，用定性自评替代；不编造数据
3. **手写优于框架**：简单场景不引入重型依赖，保持透明可控
4. **面试叙事性**：v3.0（工具）→ Agent 项目（智能体），展示产品迭代思维和技术判断力
